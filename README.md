# GitHub App governance, GitOps-managed

Which repositories each GitHub App can access is declared in this repository, changed only through pull requests,
and applied by a pipeline: `terraform plan` on every PR, `terraform apply` on merge to `main`. Every app has:
- an **owner team**
- **approved permissions**
- a **review date**, after which it loses access automatically

A daily audit finds apps **nobody registered**, **drift** (changes made by hand) and reviews coming due.

Built for a DevOps take-home: a throwaway org, [`delta-appgov`](https://github.com/delta-appgov), simulating Delta's
problem of too many apps, no ownership and no process. The scale is handled in the design write-up
([docs/GOVERNANCE.md](docs/GOVERNANCE.md)), not by creating hundreds of resources.

## How it works

```
 apps/<name>.yaml ─┐                      ┌─ validate (no secrets): fmt · validate · terraform test · risky-HCL flags
 inventory/*.json ─┼─ pull request ───────┼─ plan  (env "plan", needs approval): sticky PR comment with the
 repositories.yaml ┘                      │        per-app access diff, governance warnings, delete guard
                                          └─ merge ─▶ apply (env "production", main only) ─▶ result on the PR

 daily audit ─▶ live installations vs inventory · this repo's own protections · drift · warnings ─▶ issues
             └─▶ optional reconcile (AUTO_RECONCILE=true, on in this org): applies only changes that REMOVE access
```

| Piece | What it is |
|---|---|
| [`apps/`](apps/) | **The registry**, one YAML per app: owner, purpose, approved permissions, `review_by`, status, repositories, bypass. Field reference in [apps/README.md](apps/README.md). |
| [`inventory/inventory.json`](inventory/inventory.json) | Every installation in the org (IDs, live permissions, repository selection), generated by `scripts/inventory.sh` and reviewed like code |
| [`repositories.yaml`](repositories.yaml) | The workload repositories managed here |
| [`terraform/`](terraform/) | Repo settings, two rulesets per repo, one authoritative access resource per app, preconditions, check warnings, tests |
| [`.github/workflows/`](.github/workflows/) | `terraform.yml` (plan/apply) and `audit.yml` (daily) |
| [`scripts/`](scripts/) | Inventory, plan guard, PR comment rendering, audit issues, bootstrap |
| [`docs/`](docs/) | [Governance design](docs/GOVERNANCE.md), [decision log](docs/decisions.md), [setup guide](docs/setup.md) |

**Key mechanics:**
- **Least privilege by default.** An app sees exactly the repos in its YAML. Repos added by hand are removed on the
  next apply.
- **Quarantine instead of deletion.** GitHub won't let an installation have zero repositories. So `status:
  quarantined`, or an expired review, parks the app on the archived, read-only `app-quarantine` repo. Undoing it is
  reverting one PR.
- **Rules apps depend on are code too.** `require-pr` lists only the apps allowed to bypass it, per repo and only
  where they're installed. `branch-integrity` (no force-push, no deletion) has no bypass at all.
- **Guard rails in CI.**
  - Preconditions reject registry mistakes with a clear message: a review date too far out for the risk tier, an
    unknown repo, an app missing from the inventory, a typo in a field name.
  - Warnings (expiring reviews, unregistered apps, permission creep) appear in every plan but never block.
  - The **delete guard** refuses to delete an app that still has real access, because the provider would leave it
    on a random repository.

## Run it yourself / point it at another org

It takes about an hour, most of it in the GitHub UI.

1. **Create the org, apps and tokens.** Follow [docs/setup.md](docs/setup.md):
   1. a free org
   2. the three apps from documented permission sets, each installed on `app-quarantine` only
   3. tokens
   4. an HCP Terraform workspace in **local** execution mode (or none; see step 4)
2. **Run the bootstrap**, which is idempotent:
   ```bash
   ORG=<your-org> PREFIX=<your-org>- HCP_ORG=<your-hcp-org> scripts/bootstrap.sh --with-hcp --with-secrets
   ```
   It sets up the teams, the archived quarantine repo, environments, variables and secrets.
3. **Inventory your installations:** `GH_OWNER=<your-org> GH_TOKEN=<owner classic PAT> scripts/inventory.sh`
4. **Plan locally:**
   ```bash
   cd terraform
   export TF_CLOUD_ORGANIZATION=<your-hcp-org> TF_WORKSPACE=github-app-governance   # or: cp ../examples/local_override.tf .
   export GITHUB_TOKEN=<classic PAT: repo, read:org> TF_VAR_github_owner=<your-org> TF_VAR_app_slug_prefix=<your-org>-
   terraform init && terraform plan
   ```
   No HCP account? `examples/local_override.tf` switches to local state without touching the code.
5. **Hand it to CI:** push, open a PR, approve the `plan` environment, merge. After the first merge, add the
   governance ruleset with `scripts/bootstrap.sh --with-ruleset`.

Nothing org-specific lives in the Terraform code:
- **The org:** `TF_VAR_github_owner`, or the repo variable `GH_OWNER`, which defaults to the repo's owner.
- **App slugs:** prefix + file name, because slugs are unique across all of GitHub.
- **Installation IDs:** generated into the inventory.
- **HCP:** environment variables only.

The only file to edit by hand is `.github/CODEOWNERS` (team handles).

Offline tests need no account at all: `cd terraform && terraform init -backend=false && terraform test`.

## Acceptance criteria → where they're met

| Criterion | Where |
|---|---|
| Terraform manages which repos each app can access, with the GitHub provider | `terraform/app_access.tf`: one authoritative `github_app_installation_repositories` per app |
| Repository configuration as code where relevant | `terraform/repositories.tf`, `rulesets.tf`: settings, `branch-integrity`, `require-pr` with app bypass |
| GitOps workflow: plan on PR, apply on merge | `.github/workflows/terraform.yml`, demo trail above |
| Governance design: ownership, review, expiry, unknown apps, safe decommissioning | [docs/GOVERNANCE.md](docs/GOVERNANCE.md) |
| At least 2 apps across at least 2 repos, changes flowing through PRs | 3 apps × 3 repos; add, narrow and quarantine PRs in the demo trail |
| README to run it and point it at another org | The section above, plus [docs/setup.md](docs/setup.md) |

## Decisions and trade-offs

Full reasoning in [docs/decisions.md](docs/decisions.md). Each entry states what we gave up.

| | Decision | Main trade-off |
|---|---|---|
| D-001 | State in **HCP Terraform Free**, not S3 + GitHub OIDC | No payment card; but a static HCP token, and a 500-resource cap |
| D-002 | HCP in **local execution** mode | GitHub runs Terraform. Remote mode would let a PR's token start an apply. |
| D-003 | **Committed inventory**, not a live lookup | Deterministic, reviewable plans; can go stale, so it's diffed daily |
| D-004 | Governance repo protections set by a **human-run bootstrap**, outside the pipeline | The separation is procedural, because the token is an owner's |
| D-005 | Pipeline uses the **maintainer's own classic PATs** (accepted) | Reaches every org the account can; enterprise target is a non-owner identity |
| D-006 | **Quarantine → delete YAML → uninstall**, enforced by the delete guard | Two PRs per removal |
| D-007 | PR plans need an **approval** | `plan` executes PR code with credentials; one extra click |
| D-008 | **Expiry enforced in Terraform** | An unrelated merge can quarantine an expired app; 30 days of warnings first |
| D-009 | **0 required approvals**, single maintainer (accepted) | No four-eyes review in the demo |
| D-010 | **Public repos** | GitHub Free only offers rulesets and environment protection on public repos |
| D-011–013 | Scope cuts; teams read-only; quarantine repo archived and read-only | See the log |
| D-014 | **Every apply reconciles the latest `main`**; drift = resource changes | Learned from an incident (#9): push events can arrive late. An apply comment may include later PRs' changes. |

## Security

**Who can reach what:**

| Credential | Lives in | Reachable by | Blast radius |
|---|---|---|---|
| Apply PAT (classic, `repo` + `read:org`) | env `production`, branch policy `main` | jobs on `main` only | Everything the maintainer's account can reach (D-005) |
| Plan PAT (same scopes) | env `plan`, required reviewer | PR runs **after approval** | Same, which is why approval comes first (D-007) |
| HCP tokens | `plan` / `production` | as above | State read/write. HCP holds no GitHub credentials. |
| Audit token (fine-grained, read-only) | env `audit`, `main` only | scheduled audit | Read org installations |

**Threats handled in this repo:**
- **`terraform plan` runs PR code.** Fixed by plan approval, risky-HCL annotations for the approver, and refusing
  fork PRs.
- **A PR editing workflows to reach the apply secrets.** Fixed by the main-only environment.
- **A stolen bot key rewriting history.** Fixed by a separate `branch-integrity` ruleset with no bypass.
- **Spoofed required checks.** Fixed by pinning checks to the GitHub Actions app.
- **Supply chain.** Fixed by SHA-pinned first-party actions, a read-only provider lockfile, an exact provider pin
  and Dependabot.
- **Break-glass undone by the next merge.** Fixed by making break-glass = suspend.

**In a large enterprise I would add:**
1. Plans outside PR-controlled code: a dedicated Terraform runner, or a central reusable workflow pinned through
   the OIDC `job_workflow_ref` claim.
2. No long-lived tokens: state in our own cloud account with GitHub OIDC, a non-owner machine identity, or a GitHub
   App with `installation_repositories:write` once the provider supports it.
3. GitHub Enterprise Cloud: a private governance repo, audit-log streaming to the SIEM with alerts on
   `integration_installation.*`, and org-level required workflows.
4. At least one approval, two for high-tier apps, code-owner review, and "prevent self-review" on environments.
5. Policy as code on the plan JSON (OPA/conftest).
6. Fewer org owners, restricted repo-admin app installs, and a fine-grained PAT approval policy.

## What I left out (and why)

These were left out deliberately for the 8-hour budget (D-011). None of them is required by the acceptance
criteria:
- a governance-bot GitHub App opening PRs, e.g. for renewals or expiry
- creating the apps from manifests
- splitting the provider into App auth for repo settings plus a PAT for access
- OPA/conftest policies
- merge queue
- audit-log streaming
- state split per business unit
- selecting repos by custom property
- a scaffold command that turns the inventory into registry YAML for brownfield adoption
- tag rulesets, and a required check sourced from ci-reporter

Each one is described in GOVERNANCE.md or in the decision log.
