# GitHub App governance: the operating model

This document proposes how an organization tracks **ownership**, **review** and **expiry** of installed GitHub Apps
at scale. It also covers how to **detect an app nobody remembers installing** and how to **decommission one
safely**. The code in this repository implements the core of it. Where it doesn't, the section says so.

> **The problem:** the number of apps isn't the real issue. The issue is access nobody owns, nobody reviews and
> nobody can safely remove. Every installed app is a non-human identity with standing access to code. When one is
> forgotten, it stays an open door indefinitely.

## 1. Principles

1. **Default deny.** An app sees only the repositories listed for it in Git. "All repositories" is an exception.
2. **Every app has an accountable team.** A team, never a person, plus an escalation team for when the owner team
   disappears.
3. **Access is time-boxed.** Every app has a review date. Missing the date removes access automatically.
4. **Git is the record.** Who granted what, when, why and with whose approval is the PR history.
5. **Reversible before irreversible.** Quarantine and suspension come before uninstalling. Uninstalling can't be
   undone: a reinstall gets a new installation ID.
6. **Fail safe under uncertainty.** If nobody can show an app is needed, it loses access. Not the other way round.

## 2. Roles

| Activity | Security | Platform team | Owning team | Org owners |
|---|---|---|---|---|
| Set policy (tiers, review intervals, exceptions) | **A/R** | C | I | I |
| Run the tooling (this repo, the pipeline, the audit) | C | **A/R** | I | I |
| Request an app, justify it, renew it | C | I | **A/R** | I |
| Approve high-tier apps and exceptions | **A/R** | C | C | I |
| UI-only actions: install, suspend, uninstall, accept permission updates | C | I | I | **A/R** |
| Triage unknown apps | **A** | R | R (if claimed) | R |

A = accountable, R = responsible, C = consulted, I = informed. Keep org owners few: **any one owner can approve a
vendor's permission update** (§6).

## 3. What is tracked per app

The registry is `apps/<name>.yaml`, one file per app (field reference: `apps/README.md`):

| Question an auditor asks | Field | Enforced by |
|---|---|---|
| Who owns it? | `owner_team`, `escalation` | Required (precondition). The team must exist (check warning). Ownership also shows in CODEOWNERS. |
| Why do we have it? | `purpose`, `ticket` | Required |
| What may it do? | `approved_permissions` | Required. The live permissions come from `inventory/inventory.json`; anything beyond the approved set is a warning plus an audit issue. |
| Where may it do it? | `repositories`, `bypass` | Authoritative: Terraform makes GitHub match exactly |
| Until when? | `review_by` | Capped by risk tier. Quarantined automatically after the grace period. |
| What's its state? | `status`: `active` / `deprecated` / `quarantined` | Drives access and bypass |

The **inventory** is the reality side of the record: every installation in the org, with IDs, live permissions and
repository selection. It is generated by `scripts/inventory.sh`, committed and reviewed like code (D-003). The
daily audit diffs it against the live org.

## 4. Risk tiers and review cadence

The tier is **derived from the permissions the installation actually holds**, not from what the requester claims.
A requester can only raise it (`declared_tier`).

| Tier | Rule | Max review interval | Reviewers |
|---|---|---|---|
| **High** | Write on contents, workflows, administration, secrets, actions, environments or webhooks; any org-level permission; any rule bypass; or "All repositories" | **90 days** | Owning team + security |
| **Medium** | Any other write (checks, statuses, issues, pull requests…) | **180 days** | Owning team |
| **Low** | Read-only | **365 days** | Owning team |

The tier sets how far ahead `review_by` may be (a precondition fails the plan otherwise) and who must review. It
never gates changes on live data: an app whose permissions change can't block anybody else's PR.

## 5. Lifecycle

```
 request ──▶ install on app-quarantine ──▶ PR: YAML + inventory ──▶ merge = grant
                                                                      │
                     ┌──── renew: PR bumping review_by ◀── reminders ─┤ (30 days before)
                     │                                                │
                     ▼                                                ▼ review_by + 14 days
                  active ──── status: deprecated ──── status: quarantined ◀── (automatic on expiry)
                                                         │  suspend in UI, watch 14 days
                                                         ▼
                                              PR: delete YAML ──▶ uninstall in UI ──▶ inventory PR
```

### 5.1 Request and onboarding

1. The requester opens a PR adding `apps/<name>.yaml`: purpose, owner team, requested permissions, repositories,
   data classification, and the vendor's security and privacy information.
2. Security reviews third-party and high-tier apps: vendor posture, data residency, whether the permissions are the
   minimum needed.
3. An org owner installs the app with **"Only select repositories" → `app-quarantine`**. Terraform can't install
   apps, and an installation needs at least one repository, so the archived parking repo is the safe landing place.
4. `scripts/inventory.sh` is run, and `inventory/inventory.json` is committed **in the same PR**.
5. The plan comment shows exactly which repositories the app gains. Merge = grant.

### 5.2 Review and renewal

- Every plan, and the daily audit issue, warns **30 days before** `review_by`.
- Renewal is a PR that bumps `review_by`, answering three questions in the PR description: *Is it still used? Are
  all its permissions still needed? Are all its repositories still needed?*
- Renewal is the natural moment to **narrow**: drop repositories the app hasn't touched.
- Batch renewals per team (one quarterly PR per team) to avoid review fatigue and rubber-stamping.

### 5.3 Expiry (enforced in code, D-008)

When `review_by` plus **14 days** have passed, an active app's effective status becomes `quarantined` on the next
apply. The optional scheduled reconcile (narrowing-only) applies it without waiting for a merge. Apps marked
`business-critical` are **not cut off**: they raise an escalation warning to the `escalation` team. A missed
review must not be what takes down payments.

### 5.4 Decommissioning safely (D-006)

The order matters, and the pipeline enforces it:

| Step | Action | Why this order |
|---|---|---|
| 1 | PR: `status: deprecated`, then work through the dependency checklist below | The app keeps access but loses its bypass. Owners get notified. |
| 2 | PR: `status: quarantined` | All real repository access is gone, but the installation stays. **Undone by reverting one PR.** |
| 3 | **Suspend** the app in the UI, then watch for 14 days ("scream test") | Suspension also stops org-level permissions, which quarantine doesn't. Fully reversible. |
| 4 | PR: delete the YAML | The **delete guard** in CI only allows this for apps already parked on the quarantine repo. Otherwise the provider would leave the app on a *random* repository. |
| 5 | Uninstall in the UI, then an inventory PR | Irreversible, so it comes last. If it happens before step 4, every plan fails until a `terraform state rm` (runbook below). |
| 6 | Clean up: cancel the Marketplace plan, rotate secrets the app could read, remove vendor-side webhooks and user authorizations | Uninstalling doesn't do any of this. |

**Dependency checklist (step 1).** An app's removal can break things that don't look like they depend on it:
- rulesets or branch protection that **require a status check produced by the app** (removing the app blocks every
  merge on those repos)
- rule bypass lists (handled here automatically, per repo)
- deployment protection rules provided by the app
- `APP_ID` / `PRIVATE_KEY` secrets in other repos or at org level
- workflows that call the app's API
- runner controllers
- the vendor-side configuration

**Runbook: an app was uninstalled out of band.** The provider can't read a deleted installation, so plans fail.
1. Run `terraform state rm 'github_app_installation_repositories.this["<name>"]'` locally against the HCP workspace.
2. Open a PR removing the YAML and refreshing the inventory.

### 5.5 Break-glass: an app is compromised

1. **Suspend it now** (any org owner, in the UI). Terraform doesn't manage suspension, so no apply will undo it, and
   the spike confirmed plans keep working on a suspended installation (S5).
2. Open a fast-track PR setting `status: quarantined`. It applies even while the app is suspended.
3. Rotate whatever the app could read. Then decommission normally.

Removing access in the UI is **not** break-glass: the next unrelated merge would re-grant it, because Git still
says so. If the pipeline itself is the problem, revoke its tokens and lock the HCP workspace.

### 5.6 Reconciliation, drift and missed triggers

- **Every apply converges on current `main`** (D-014). It doesn't replay a commit. A push event that arrives late,
  twice or never is therefore harmless: the next apply, or a manual `workflow_dispatch`, brings GitHub back to
  `main`. This was learned the hard way (#9).
- **Drift** is any difference between `main` and live GitHub, e.g. a repo admin adding their repo to an app in the
  UI. The daily audit opens a drift issue with the exact per-app difference, and the issue closes itself once
  GitHub matches again.
- **Automatic reconcile** (`AUTO_RECONCILE=true`, enabled in the demo org) applies only changes that **remove**
  access. It never grants or re-grants: an owner may have removed access on purpose during an incident, and that
  needs a human and a PR.

## 6. Detecting an app nobody remembers installing

### 6.1 Which signals exist, by GitHub plan

| Signal | Free / Team | Enterprise Cloud |
|---|---|---|
| List of installations: IDs, permissions, repository selection, created/suspended timestamps (`GET /orgs/{org}/installations`) | ✅ (owner, or *Administration: read*) | ✅ |
| Who installed it, and when | Audit log **UI only**, owners only, **180 days** | Audit log API + streaming to a SIEM |
| Real-time install events | ❌ (`installation` webhooks go to the *app*, not the org) | Audit-log streaming (`integration_installation.*`) |
| Is it actually used? | Indirect only: commits, comments and check runs authored by `app/<slug>`. **Read-only apps leave no trace.** | API-request events for security-relevant endpoints, plus token metadata |
| A "last used" field | ❌ doesn't exist | ❌ doesn't exist |

The honest conclusion: **"unused" can't be proven**, especially for read-only apps and outside Enterprise. So the
policy keys on **ownership**, not on usage.

### 6.2 What runs here

The daily `audit` workflow:
- compares the live installations with the committed inventory: a new app, a reinstall (new ID), a permission
  change an owner accepted, a suspension or an uninstall
- compares the inventory with the registry: unregistered apps, and apps on "All repositories"
- turns each finding type into one GitHub issue, which closes itself when the finding is gone

The same warnings appear in every plan comment, so nobody can miss them while changing something else.

### 6.3 The claim process (fail-safe)

1. **Day 0.** The audit opens an issue. Security labels it and gathers forensics:
   - the installer and the date, from the audit log
   - the vendor and the requested permissions
   - which repos it can see
   - any activity by `app/<slug>`
2. **Days 0–14: claim window.** The issue is announced in engineering channels. A team adopts the app by opening a
   registry PR: owner, purpose, minimum repositories. The PR gets the normal review.
3. **Day 14, unclaimed.**
   1. Narrow it to `app-quarantine`. If it was registered at some point, use `status: quarantined`. If not, an org
      owner changes its repositories in the UI.
   2. **Suspend it.** Breakage now surfaces as complaints, which is the scream test.
4. **Day 30, nobody objected.** Uninstall it and close the issue with the forensics attached.

## 7. What automation can and can't do

| Action | As code? | How it's done |
|---|---|---|
| Grant, narrow or quarantine an app's repository access | ✅ | PR → apply |
| Rule bypass for an app; required checks from an app | ✅ | PR → apply |
| Install an app | ❌ | UI, org owner (or a repo admin, for low-permission apps; restrict this) |
| Uninstall or suspend a third-party app | ❌ (needs the app's own credentials) | UI, org owner |
| Switch "All repositories" → selected | ❌ | UI |
| Accept a vendor's permission update | ❌ | UI. **Any one owner can**, and every owner is emailed. Policy: only together with a registry PR. |
| Remove an app's last repository | ❌ (API returns 422) | Park it on `app-quarantine` |

## 8. Rolling this out at Delta's scale

This repository manages four apps and three repositories. At Delta's scale, assume **300 installed apps across
2,000 repositories**, most of them added before anyone tracked anything.

### 8.1 Brownfield adoption in waves

1. **Inventory everything.** `scripts/inventory.sh` lists every installation. A scaffold step (roadmap) writes a
   registry YAML per app with `owner_team: unknown`, the current repositories and `review_by: +30 days`.
2. **Adopt in waves of 20–30 apps, highest tier first.** Each wave's first plan **must be a no-op**: the YAML
   describes today's reality, and nothing changes yet. (The spike showed the provider adopts an existing
   installation without an import step; `import` blocks make that explicit.)
3. **Run an ownership campaign with deadlines and an executive sponsor.** Infer likely owners from repo admins and
   CODEOWNERS of the repositories each app touches.
4. **Narrow afterwards.** Once an app has an owner, its next review drops repositories it doesn't need.
5. **"All repositories" installs need a manual campaign**, because only the UI can change them. Do the high tier
   first.
6. Anything unclaimed after the campaign goes through the claim process (§6.3).

### 8.2 Scale limits, in numbers

| Concern | Estimate at 300 apps × 2,000 repos | Consequence |
|---|---|---|
| API calls per full plan | ~300 calls (one installation list each) + 2–3 per managed repo + 1 per ruleset ≈ **8,000–10,000** | Over a PAT's **5,000 requests/hour**. Split the state, and give the app-access state its own small footprint (~300 calls). |
| Managed resources | 300 installation + 2,000 repo + 4,000 ruleset resources ≈ **6,300** | HCP Free caps at **500**. Use a paid tier or a self-managed backend (D-001). |
| Repository lists | Large apps list hundreds of repos | Select repos by **custom property** (e.g. `team = payments`) instead of listing them (roadmap). |
| Concurrency | One state means one lock: PRs queue behind each other | One state for app access, plus per-business-unit states for repository configuration owned by a repo platform |

The design scales because the registry is **one file per app**: small diffs, per-file ownership, no merge conflicts
between teams.

## 9. Exceptions

Exceptions are time-boxed, have a named approver from security, and go through the same expiry loop. Examples: an
app that genuinely needs "All repositories", or a high-tier app that needs a longer review interval. An exception
is recorded as `declared_tier` plus a `ticket` in the app's YAML. **An exception without an end date doesn't exist.**

## 10. Metrics

Report these monthly:
- % of apps with a valid owner team (team exists, ≥ 2 active members)
- % of apps past `review_by`
- number of "All repositories" installs
- number of high-tier apps
- number of unregistered apps, and the median time to quarantine one
- number of drift issues opened per month (manual changes outside Git)
- number of apps narrowed at renewal

## 11. Adjacent risks: the same problem in other forms

GitHub Apps are one kind of non-human access. Apply the same model to the others:

- **OAuth apps.** Keep the org's OAuth app access restrictions on (the default only for newer orgs). Approve OAuth
  apps through the same request PR.
- **Personal access tokens.** Require approval for fine-grained PATs, set a maximum lifetime, and restrict classic
  PATs once nothing needs them. This repo still does need one (D-005).
- **Deploy keys.** The API shows `read_only` and `last_used`. Write-enabled keys can be ruleset bypass actors, so
  review them like apps.
- **Repo admins installing apps.** Repo admins can install apps that request no org-level permissions on their own
  repositories, and add their repositories to existing installations. That is the main source of drift; restrict it
  in the org settings.
- **Few org owners.** Each owner can approve a vendor's permission update on their own. Keep the owner count small,
  and alert on the audit-log event for it (Enterprise).
- **Private forks to personal accounts.** These move code outside the org's app governance. Disable private forking.

## 12. Hardening this for an enterprise

See the README's *Security* section. In short:
- run plans outside PR-controlled code (a dedicated Terraform runner, or a central reusable workflow)
- no long-lived tokens: a non-owner machine identity, or a GitHub App with `installation_repositories:write` once
  the provider supports it, with short-lived credentials
- a private governance repo on Enterprise Cloud with audit-log streaming
- policy as code on the plan JSON (e.g. "high-tier apps can't be granted repos tagged `restricted`")
- at least one approval for every change, and two for high-tier apps
